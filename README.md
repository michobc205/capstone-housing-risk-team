# County-Level Housing Price Decline Prediction — Team Repo

Neuefische Data Science Bootcamp — Capstone Project (Team Merge)

Merges two independently-built pipelines — a pandas-based approach and a
SQL/Postgres-based approach — into a single shared codebase, comparing
methodology and combining the best of both along the way.

## Business Question

> "Can we predict, one quarter ahead, which US counties will see a housing
> price decline greater than 2%, and how much predictive power does
> mortgage-rate movement (30-year fixed rate level and rate-of-change) add
> once a county's own price momentum is already known?"

## Data Sources

| Source | Grain | What it provides |
|---|---|---|
| Zillow ZHVI (Middle Tier, 33rd-67th percentile, SFR + Condo/Co-op, Smoothed & Seasonally Adjusted) | County, monthly | Home value index — builds the price-decline label and momentum features |
| FRED `MORTGAGE30US` | National, weekly (resampled to monthly via `.mean()`) | 30-year fixed mortgage rate — builds rate level, rate-of-change, and interaction features |

## Merge Workflow

This repo combines two independently-built capstone pipelines:

- **[housing-price-decline-risk-sql](https://github.com/michobc205/housing-price-decline-risk-sql)** — Michel's SQL/Postgres-based approach, doing transformations (splitting, EDA, feature engineering) directly in Postgres via SQL rather than pandas
- **Housing Price Decline** — Jolenn's pandas-based approach, using Python/pandas for transformations with Postgres as storage only

Each phase is merged by comparing both independent implementations, resolving any methodology differences, and combining them into a single version carried forward here. Decisions made along the way are documented directly in the relevant notebook's markdown cells, not hidden in commit messages.

### Phase 1 — Ingest, Join, and Coverage Audit ✅ Complete

**Notebook:** `notebooks/01_phase1_ingest_merged.ipynb`
**SQL:** `sql/001_schema.sql`, `sql/002_join_check.sql`, `sql/phase1_validation.sql`

Merges both repos' Zillow ZHVI + FRED `MORTGAGE30US` ingest pipelines. Key decisions:

- **Zillow NaN handling:** adopts the pandas repo's approach — trims each county to its own reporting window but keeps genuine *internal* gaps as NULL rows, rather than silently dropping them
- **Month storage convention:** adopts month-end dates (Zillow's native format), removing the need for a `date_trunc`-based join
- **The join itself stays in SQL** (the SQL variant's differentiator), now simplified to a plain equality join since both tables share one date convention
- **Label rule: both quarter-end months required.** A county-quarter is represented by its quarter-end month (March, June, September, December), and a decline label needs two consecutive quarter-end values, as in the pandas repo's `labels.py`. The earlier SQL used the last month with a value, which gave labels that spanned two, or four to five, months. The same rule is used in `phase1_validation.sql`, `004` and `005`

**Result:** the joined table `county_month_joined` (Zillow as the spine, LEFT JOIN to `mortgage_monthly`) holds 709,996 county-months across 3,071 counties, with no rows or counties dropped by the join.

**Aggregation sensitivity:** the weekly-to-monthly FRED resample uses `.mean()` at month-end. A separate check comparing `.mean()` against `.last()` found the two nearly identical in level (correlation 0.9992) but disagreeing on the direction of the month-over-month change in 111 of 665 months, so the choice matters for the rate-of-change feature and is documented here rather than left implicit.

**Validated two independent ways:** once via the notebook's own pandas-based provenance check, and again via `sql/phase1_validation.sql`'s pure-SQL recomputation. Both give the same figures on 709,996 rows and 3,071 counties: Train 173,277 (4.88%), Embargo 3,020 (0.96%), Test 52,085 (8.15%) and Full history 231,453 (5.55%). The Train count is exactly the pandas repo's label count. Full history is Train, Embargo and Test (228,382) plus 3,071 rows for 2026-Q2; the unfinished 2026-Q3 gives no rows, because its quarter-end month (September) is not published yet. The Phase 0 figures (Train 173,824 / 4.96%, Embargo 3,021, Test 52,087) came from an earlier method. The Train count is 547 lower: 90 rows because 91 counties each have one quarter with all three months empty (the earlier method kept the quarter after it, whose change spans six months), and 457 rows whose quarter-end month was empty but whose quarter had an earlier value. `docs/phase0_framing.md` keeps the original table and adds a note with these figures.

### Phase 2 — Chronological Split + CV Folds ✅ Complete

**Notebook:** `notebooks/02_phase2_split_cv.ipynb`
**SQL:** `sql/003_phase2_split.sql`, `sql/003b_cv_fold_membership.sql` (plus `sql/005_phase4_features.sql`, which builds the modeling table the fold view reads)

Merges the SQL variant's single chronological split with the pandas repo's cross-validation folds. Key decisions:

- **Split:** Train through 2021-09-30, one-quarter Embargo (2021-Q4, excluded from both sides), Test 2022-01-01 to 2026-03-31, and anything later is labelled `unassigned` rather than silently dropped
- **CV folds:** the pandas repo's 11 expanding-window folds (validation years 2010-2020, four quarters each) are stored in a `cv_folds` table, all inside the Train window; folds never touch Embargo or Test
- **Fold membership:** the `cv_fold_rows` view assigns each Train county-quarter to each fold as `train` or `val`, converting quarter-start dates to quarter-end to match the fold boundaries
- **NULL ZHVI months:** some counties have missing ZHVI months mid-series, so quarterly snapshots use the quarter-end month only and a label needs both quarter-end months (the previous row must be the calendar quarter before it), the same rule as the pandas labels (see Phase 1)
- **No embargo gap inside the folds (decision: documented, no gap).** Training ends the quarter before validation starts. Every training label is already known when the validation features are measured, and the features only look backward, so this matches real use. The Train/Test embargo is stricter on purpose, because Test must stay out of every model choice
- **Folds are applied by label quarter**, while the pandas notebook applies them by feature quarter. Both are free of leakage, but fold scores are not comparable one-to-one with `baseline_lock.json` (mean ROC-AUC 0.854, pooled prevalence 3.62% against about 3.8% here)

**Validated:**

- The split covers all 709,996 rows, the same buckets as the pandas split (Train 529,214, Embargo 9,063, Test 156,364, Unassigned 15,355; difference 0). The 1,043 rows above the earlier SQL-variant monthly counts are exactly the kept NULL-ZHVI months (1,040 Train, 3 Test)
- Modeling table (built by `005`): Train 164,460 rows (4.85% positive), Embargo 3,020, Test 51,980 (8.11% positive)
- Every validation fold has at least 71 positives (the minimum required is 20); pooled validation is 112,734 rows with 4,252 positives, a prevalence of 3.77%
- No Embargo or Test rows appear in any fold
- The fold and modeling-table figures were first reproduced on a second machine (PostgreSQL 15, Jolenn's laptop) under the earlier label rule, and `005` and `003b` were then repeated there with the current files: the modeling table gave the same counts (Train 164,460, Embargo 3,020, Test 51,980, Unassigned 3,070) and the fold view has 22 rows, with the lowest validation fold at 71 positives

**Note:** the pandas repo's test set has 48,960 rows against 51,980 here. This is a dating convention, not a county filter: its rows are dated by feature quarter, so it covers 16 label quarters (2022-Q2 to 2026-Q1) against our 17 (2022-Q1 to 2026-Q1). The team agreed in Phase 4 to carry forward the label-quarter convention (17 test quarters). Counted by feature quarter, our table has exactly her 48,960 rows.

### Phase 3 — EDA: Lag Sweep and Reverse-Causation Check ✅ Complete

**Notebook:** `notebooks/03_phase3_eda_merged.ipynb`
**SQL:** `sql/004_phase3_eda.sql`
**Results written by the notebook (in `outputs/`, not tracked in git):** `phase3_lag_correlation.csv`, `phase3_lag_correlation_quarterly.csv`, `phase3_reverse_causation.csv`

Merges the SQL variant's quarterly label and lag correlation with the pandas repo's EDA (p-values, confidence intervals, reverse-causation check). Key decisions:

- **Rate-of-change in percentage points:** `rate(t) - rate(t - lag)`, as in the pandas repo. The earlier SQL used relative change, which gave a weaker 12-month correlation (-0.034 against -0.051)
- **Preceding-quarter alignment:** each label is paired with the rate change at the end of the quarter before it, which is what predicting one quarter ahead requires. The pandas EDA paired it with the same quarter; that version is kept only to reproduce its numbers
- **Label:** a decline strictly greater than 2%, using the quarter-end month only; a label needs both quarter-end months (see Phase 1)
- **Lag:** 12 months
- **Reverse-causation check in SQL:** two variants, one with the full mortgage-rate history (as in the pandas notebook) and one using only rates up to the end of Train

**Validated:**

- The quarterly label has 173,277 rows (4.88% positive), matching the Phase 1 check and the pandas repo's label exactly
- The SQL reproduces the pandas lag sweep: with the same-quarter setup, every lag agrees to six decimals (12 months: -0.0521 against -0.0521)
- The 12-month lag has the largest correlation on both alignments; in the one-quarter-ahead version r = -0.0506 (95% CI -0.0554 to -0.0459, n = 169,091). The effect is weak and its sign inconclusive: the rate change is one national number per quarter, so the 170,000 rows are not independent evidence. A quarter-level re-test (82 quarters) gives r = -0.145 with a 95% CI of -0.351 to +0.074 and p = 0.19, which includes zero. The same holds for all six lags, so the 12-month lag cannot be told apart statistically from the others. It is carried forward because it was fixed in advance
- Reverse causation: the SQL reproduces the pandas result exactly (14 months, r = 0.2637), but using only rates up to the end of Train roughly halves it (r = 0.12), so there is no reliable evidence that home prices lead mortgage rates. Its intervals assume independent months, which they are not (3-month momentum overlaps and both series are autocorrelated), so they are too narrow and variant B's lower bound near zero is not reliable
- The SQL was tested on synthetic data in a scratch PostgreSQL 16 database against independent pandas versions (agreement to about 1e-16). That test predates the label-rule change; the comparison with the pandas repo's real results above covers the new rule
- Reproduced on a second machine (PostgreSQL 15, Jolenn's laptop): the reverse-causation sweep matched exactly (variant A: 14 months, r = 0.2637; variant B: 4 months, r = 0.1238)

**Agreed with the pandas repo's author:** percentage points, the preceding-quarter alignment, the strict 2% threshold and the 12-month lag. The missing-month handling was later changed to her quarter-end rule (see Phase 1).

**Agreed wording (reverse causation):** "No reliable evidence that home prices lead mortgage rates." Jolenn's notebook 11 and the notebook 10 paragraph that cites it should use the same sentence (her notebook 11 had called the feedback-loop explanation supported).

**Repeated on Jolenn's laptop:** Phase 3 (`004` and notebook 03) was re-run there with the current files and gives the same results as here: the 12-month lag, one quarter ahead, has r = -0.0506 (95% CI -0.0554 to -0.0459, n = 169,091), and the quarter-level re-test gives r = -0.145 (95% CI -0.351 to +0.074, p = 0.19, 82 quarters). Her `outputs/` and database now use the quarter-end label rule.

### Phase 4 — Feature Engineering ✅ Complete

**Notebook:** `notebooks/04_phase4_features_merged.ipynb`
**SQL:** `sql/005_phase4_features.sql`, `sql/003b_cv_fold_membership.sql`
**Results written by the notebook (in `outputs/`, not tracked in git):** `phase4_feature_summary.csv`

Merges the SQL variant's modeling table with the pandas repo's feature matrix: six features measured one quarter before each label (1, 3 and 6-month price momentum, the mortgage rate level, its 12-month change, and the interaction). Key decisions:

- **Rate-of-change in percentage points,** as in Phase 3 and the pandas features. The earlier SQL used relative change
- **Interaction = rate change x 3-month momentum,** the pandas choice (3 months is one quarter, the prediction horizon). The earlier SQL used 1-month momentum; Phase 5 can test 1 and 6 months
- **Features come from the preceding quarter,** and rows are dated by their label quarter (the convention behind the Phase 0 counts). The pandas matrix is dated by feature quarter
- **A row is dropped if any of the six features is missing,** so no model input holds an empty value. The earlier SQL only checked two of them
- **Both quarter-end months are required** (decided after comparing the two builds row by row): the label and the features use the quarter-end month only, as in the pandas repo. The earlier SQL used the last month with a value, which gave 448 extra Train rows
- **Column names follow the pandas features** (`momentum_1m`, `momentum_3m`, `momentum_6m`, `mortgage_rate_level`, `mortgage_rate_roc`, `rate_roc_x_momentum`), plus a `feature_quarter_end` column so the two tables can be joined row by row

**Validated:**

- The table has 222,530 rows (Train 164,460, Embargo 3,020, Test 51,980, Unassigned 3,070), no missing features, one row per county and quarter, features measured at the preceding quarter end, and the interaction equals the plain product
- Train: 164,460 rows, 3,009 counties, 4.85% positive, identical to the pandas matrix (also matching her `train_features_meta.json`). Both cover the same counties
- Row by row, the SQL table and the pandas matrix hold exactly the same 164,460 rows, with identical feature values (largest difference 8.9e-16) and identical labels. Before the label rule was tightened the SQL table had 448 extra rows (0.27% of Train). Each had an empty quarter-end month in the feature quarter (199 rows, declines 53% of the time), in the label quarter (237 rows, 2.5%) or in both (12 rows), so its label did not span exactly one quarter, and together they held about 25% declines against 4.9% overall
- Test: 51,980 rows (17 label quarters). Dated by feature quarter, as the pandas matrix is, the same rows number 48,960, exactly her 48,960, so the dating convention alone explains the test-set difference
- All 11 validation folds keep at least 71 positives and no Embargo or Test row enters any fold after the rebuild
- The SQL logic was first tested on synthetic data in a scratch PostgreSQL 16 database and confirmed on Jolenn's laptop, both before the label-rule change. The current `005` and `003b` were then repeated on her laptop: Train 164,460 rows, 3,009 counties, 4.85%, identical to her `train_features.csv` row for row (largest feature difference 4.4e-16, 0 label mismatches), and the other splits match the figures above. Phase 3 and Phase 4 were re-run there as well (see Phase 3), and notebooks 01 and 02 were confirmed there too, with no differences reported. `phase1_validation.sql` was run there with the current files on 2026-10-05 and gave the same figures as here (Train 173,277 / 4.88%, Embargo 3,020 / 0.96%, Test 52,085 / 8.15%, Full history 231,453 / 5.55%)

**Agreed with the pandas repo's author:** percentage points for the rate change, the 3-month interaction, rows dated by label quarter (17 test quarters), the pandas column names, and dropping any row with a missing feature.

**Decision made:** the SQL requires the quarter-end month in both quarters, as the pandas version does. That removed the 448 extra rows, so the two builds now match exactly.

### Phase 5 — Modeling on the Validation Folds ✅ Complete

**Notebook:** `notebooks/05_phase5_modeling_merged.ipynb`
**Locked result (committed):** `docs/phase5_baseline_lock.json`
**Rules written before the notebooks were compared:** `docs/merge_rules_phase5_6.md`
**Tables written by the notebook (in the database):** `phase5_fold_scores`, `phase5_step_summary`, `phase5_bootstrap_deltas`, `phase5_validation_predictions`

Merges the SQL variant's modeling notebook with the pandas repo's modeling sequence (`08` and `09`). The pandas repo's code depends on its `src/housing_risk/` package, which the team did not bring in: the SQL variant's notebook needs only pandas, NumPy, SQLAlchemy with the psycopg2 driver, scikit-learn and python-dotenv, so it was ported with the team column names. Key decisions:

- **Design fixed before any result:** three families (logistic regression, random forest, histogram gradient boosting), fixed settings, seed 42, no tuning; three feature steps in the Phase 0 order (momentum only, plus rate level, plus rate change and interaction, with the 12-month lag fixed in advance); every choice made on the 11 validation folds
- **XGBoost is left out.** Histogram gradient boosting is the same kind of model, and three families already meet the requirement of at least two
- **The recommended model is chosen on validation only:** the family and step with the highest mean ROC-AUC over the 11 folds, and nothing is re-selected afterwards
- **A step helps only if its 95% interval excludes zero and its gain is at least +0.01 ROC-AUC.** The interval comes from a bootstrap that resamples the 44 validation quarters (2,000 draws), scoring each fold on its own and averaging the fold scores
- **A check, not the main result:** a second bootstrap on pooled out-of-fold predictions (the pandas repo's method). If the verdicts differ, the main verdicts stand and the difference is reported
- **Added after the comparison, and labelled in the notebook:** the validation year and PR-AUC divided by each fold's base rate in the per-fold tables, a quarter-bootstrap interval for the interaction coefficient (exploratory), and a sentence that the lifts depend on the fixed step order
- **Baseline lock:** the baseline scores are written to `docs/phase5_baseline_lock.json`, and the notebook stops until that file is committed, so the reference point is fixed before steps 2 and 3 are fitted
- **Reproduction check:** the baseline must reproduce the baseline locked by the SQL variant. If it does not, the notebook stops and nothing is locked
- **Tolerance (decided 2026-10-06):** logistic regression and histogram gradient boosting must reproduce the reference to within 1e-6, so any difference in the data or the code stops the notebook. The random forest is allowed 1e-3: on the second machine its trees split differently at near-ties (a gap of 3.85e-04), while the other two families matched exactly. The step verdicts depend on gains of at least +0.01, far larger than this tolerance
- **Test:** the Test period was scored in both independent pipelines and in earlier versions before this merge, so the results are protected from new choices but not untouched. Every choice here was made on the validation folds, and Test is scored with frozen models in Phase 6

**Validated:**

- Folds: 11 folds, 44 validation quarters, 112,734 validation rows and 4,252 declines, lowest fold 71. Only Train rows are used, and each training window ends before its validation window
- Mean ROC-AUC over the 11 folds, momentum only / plus rate level / plus rate change and interaction: logistic regression 0.8364 / 0.8368 / 0.8372, random forest 0.8680 / 0.8564 / 0.8462, histogram gradient boosting 0.8666 / 0.8525 / 0.8511
- **No step helps in any family.** The logistic regression changes are tiny (+0.0005, +0.0004, +0.0008, with intervals that include zero and upper ends of at most +0.0024). Adding the rate level lowers ROC-AUC for the random forest (-0.0116, 95% interval -0.0173 to -0.0002, borderline) and for histogram gradient boosting (-0.0141, -0.0206 to -0.0042). Step 3 compared with step 2 shows no significant change in any family. Once a county's own momentum is known, the mortgage rate adds no measurable predictive power on the validation folds
- **Recommended model, chosen on validation:** random forest on momentum only (mean ROC-AUC 0.8680, PR-AUC 0.3120, mean base rate 4.21%). Histogram gradient boosting is within 0.002, and logistic regression has the highest PR-AUC (0.3290), so the choice between families is not a strong one
- **Check bootstrap:** 6 of the 9 verdicts agree with the main bootstrap, and none says "helps" under either method. The three differences are all "hurts" under one method and "no significant effect" under the other (random forest step 2, random forest step 3 against step 2, histogram gradient boosting step 2)
- **Interaction coefficient:** +0.2275 (standardized), 95% quarter-bootstrap interval +0.0306 to +0.3814 (1,000 draws over the 82 Train quarters). It is positive, the opposite of the expected negative sign, and it is read as exploratory: it shows an association inside Train, while the validation results show no gain from adding the rate features. The 1-month and 6-month momentum variants of the interaction were not tried
- **Rates outside the training range:** the rate level lies outside the training range for all validation rows in folds 0 and 2, about a quarter in folds 1 and 3, and half in fold 10. The rate change is outside it only in fold 4 (24.8%). This may contribute to the drop in the tree models but does not explain all of it
- **Reproduced on the original machine** (Windows, Python 3.13.9, numpy 2.5.3, pandas 3.0.6, scikit-learn 1.9.1, PostgreSQL 18): the team database gives the SQL variant's locked baseline exactly (largest gap 0.00e+00 in all three families), in two full runs
- **Reproduced on a second machine** (Jolenn's Apple Silicon Mac, Python 3.14.7, the same numpy, pandas and scikit-learn versions, PostgreSQL 15): logistic regression and histogram gradient boosting matched with a gap of 0.00e+00, the random forest within 3.85e-04, and all 9 step verdicts, the recommended model, the check bootstrap and the interaction coefficient matched. The whole notebook ran in 3 minutes 16 seconds there. The closest call is the random forest with the rate level added: its interval ends at -0.0002 on the original machine and -0.0001 on the second, so "hurts" holds on both

**Reading the results:** treat the rate inputs as exploratory (about 82 independent quarters of information), the 12-month lag was fixed in advance, and fold scores are not comparable one-to-one with the pandas repo's `baseline_lock.json`, because that file dates its folds by feature quarter.

### Phase 6 — Evaluation on the Test Period ✅ Complete

**Notebook:** `notebooks/06_phase6_evaluation_merged.ipynb`
**Locked results (committed):** `docs/phase6_thresholds_lock.json` (the F1 cut-offs, found on the validation predictions, and the columns of the three feature steps; committed before Test was scored) and `docs/phase6_test_lock.json` (the Test scores of the nine frozen models)
**Rules written before the notebooks were compared:** `docs/merge_rules_phase5_6.md`
**Tables written by the notebook (in the database):** `phase6_test_scores`, `phase6_test_deltas`, `phase6_family_deltas`, `phase6_thresholds`, `phase6_decision_rules`, `phase6_calibration`, `phase6_calibration_all`, `phase6_per_quarter`, `phase6_range_check`, `phase6_eval_summary` and `phase6_test_predictions` (county level: it stays in the database and is never exported)

Merges the SQL variant's evaluation notebook with the pandas repo's final evaluation (`10`). The pandas notebook scores two models on its own feature build. The SQL variant's notebook scores the nine frozen models of Phase 5 on the shared modeling table and adds the decision rules, the calibration, the per-quarter stability and the range check, so it was ported with the team column names. From the pandas notebook the team took the order-dependency statement, the idea of a data-quality gate on the Test window (here with exact figures) and a plain read-out against the project's success criteria. Its second algorithm is left out, as in Phase 5, and its feedback-loop explanation of the rate-change sign is not carried over (the reverse-causation check itself was merged in Phase 3, with the wording agreed there). Key decisions:

- **Design fixed before any result:** the nine models of Phase 5 (three families, three feature steps) with the same fixed settings, refit on all Train rows. Every choice was made on the validation folds, and Test is scored with frozen models. Test was also scored in earlier, retired versions of both pipelines, so it is not a fresh draw: nothing in the notebook is chosen from Test results
- **Locks and gates:** the baseline lock must be committed before the notebook runs. The F1 cut-offs are computed from the validation predictions only and written to `docs/phase6_thresholds_lock.json`, and the notebook stops until that file is committed, before Test is scored. The Test scores are then written to `docs/phase6_test_lock.json`, and the notebook stops again until that file is committed, before the analysis continues
- **Data-quality gate and port checks:** the notebook stops unless Train has 164,460 rows and Test has 51,980 rows, 4,214 declines and 17 label quarters (2022-Q1 to 2026-Q1), and unless the last Train label ends before the first Test label quarter starts. The validation predictions must have 11 folds, 44 quarters, 112,734 rows and 4,252 declines, at least 20 declines in every fold, no duplicate county and quarter, and every row inside Train with the same label as in the modeling table
- **Cut-offs are frozen:** a re-run recomputes them only as a check and then applies the committed cut-offs, so every machine uses the same decision rule
- **Decision rules:** the riskiest 5%, 10% and 20% of counties in each quarter, and the validation-locked F1 cut-off, reported side by side and judged by lift. No rule is picked
- **Does the rate help on Test?** The same rule as Phase 5 (the 95% interval excludes zero and the gain is at least +0.01 ROC-AUC), with a bootstrap that resamples the 17 Test quarters (2,000 draws)
- **Tolerances:** logistic regression and histogram gradient boosting must reproduce the reference to within 1e-6 (cut-offs and Test scores). The random forest keeps 1e-3 for the Phase 5 baseline (decided 2026-10-06) and is allowed 1e-2 for its Test scores and for its two F1 checks on a re-run (decided 2026-10-07, after the second machine showed a gap of 1.43e-3 in its PR-AUC; the F1 curve of a random forest is flat near its top, so its best cut-off can move by a few thousandths between machines while the F1 hardly changes). The row counts must match exactly
- **Feature steps recorded:** the thresholds lock lists the columns of all three feature steps, and the notebook stops unless they match the fixed lists and the committed baseline lock
- **Added after the comparison, and labelled in the notebook:** a paragraph on the fixed step order and, added after Test was seen, a plain read-out of the verdicts against the success criteria (it computes nothing new)

**Validated:**

- Gates: Train 164,460 rows; Test 51,980 rows, 4,214 declines (8.11%) and 17 label quarters; validation predictions 112,734 rows and 4,252 declines
- Test ROC-AUC at the baseline: logistic regression 0.8668, random forest 0.8857, histogram gradient boosting 0.8915. All nine models score higher on Test than on their validation average, by 0.017 to 0.034 ROC-AUC
- **No step helps in any family on Test.** Adding the rate level lowers ROC-AUC for the random forest (-0.0077, 95% interval -0.0118 to -0.0044) and for histogram gradient boosting (-0.0223, -0.0414 to -0.0084), and leaves logistic regression unchanged (+0.0009, -0.0021 to +0.0035). Step 3 compared with step 2 shows no significant change in any family. Once a county's own momentum is known, the mortgage rate adds no measurable predictive power on Test either, including the 2022-23 hiking cycle. Test has only 17 quarters, so the intervals are wide
- **The recommended model is unchanged (chosen on validation):** random forest on momentum only, with Test ROC-AUC 0.8857 (95% interval 0.8502 to 0.9139) and PR-AUC 0.4665 (0.3379 to 0.5738) against a base rate of 8.11%. At the baseline, histogram gradient boosting is ahead of the random forest by 0.0058 (0.0022 to 0.0107) and the random forest is ahead of logistic regression by 0.0189 (0.0008 to 0.0470). The difference is reported and does not change the choice
- **Decision rules (recommended model):** the riskiest 10% of counties in each quarter hold 48.6% of the Test declines, and 39.4% of the flagged counties declined (lift 4.9). The lifts for the top 5%, 10% and 20% are 6.0, 4.9 and 3.5 on Test against 7.8, 5.5 and 3.6 on validation. The F1 cut-off (0.3386) flags 6.3% of Test counties against 4.6% on validation, and its lift falls from 10.7 to 6.9, so it is the least stable of the four rules
- **Calibration:** the probabilities are too low on Test (6.91% predicted against 8.11% actual, below the actual rate in all ten deciles) and were too high on validation (5.39% against 3.77%). The gap is smallest in the riskiest tenth. No recalibration is applied
- **Stability over time:** the quarterly ROC-AUC runs from 0.7555 (2022-Q1, 39 declines) to 0.9637 (2026-Q1), with a median of 0.9015, and 12 of the 17 quarters are at or above 0.85. Four of the five quarters below 0.85 are in 2022-23, the fifth is 2025-Q2
- **Rates outside the training range:** the rate level lies outside the Train range for 5.9% of Test rows (all in 2023-Q4: 7.20 against 7.16). The 12-month rate change lies outside it for 29.4%, every county in the five quarters from 2022-Q3 to 2023-Q3 (up to +3.27 points against at most +1.11 in Train)
- **Reproduced on the original machine** (Windows, Python 3.13.9, numpy 2.5.3, pandas 3.0.6, scikit-learn 1.9.1, PostgreSQL 18): the F1 cut-offs reproduce the SQL variant's to about 1e-16, and all 27 Test numbers (nine models, ROC-AUC, PR-AUC and Brier score) reproduce its Test scores (largest gap 0 for logistic regression and histogram gradient boosting, 7e-18 for the random forest), in a fresh run and in a second run from the committed locks
- **Reproduced on a second machine** (Jolenn's Apple Silicon Mac, Python 3.14.7, the same numpy, pandas and scikit-learn versions, PostgreSQL 15): a first re-run stopped, as designed, at the check of the Test scores (logistic regression 7e-17, histogram gradient boosting 0, random forest PR-AUC 1.43e-3, against the 1e-3 allowed at that time), which led to the 1e-2 tolerance above. The second re-run ran to the end. The bootstrap verdicts and every `interval_excludes_zero` value in the family comparison are the same as on the original machine, and the random forest intervals differ only in the third or fourth decimal (baseline Test ROC-AUC 0.8861 against 0.8857). Its random forest cut-offs moved by up to 3.4e-3, and the F1 at the locked cut-off was up to 1.12e-3 below that machine's own best

**Reading the results:** use the models to rank counties, not to read off a probability, because the probabilities are not stable across periods. The rate inputs are exploratory (about 82 independent quarters of information) and Test has only 17 quarters. "No gain" is not "no relationship": it says the rate adds nothing measurable beyond a county's own price momentum, which is the question the project asks.

## Setup

This project uses a plain Python virtual environment (no Anaconda required):

```
python -m venv .venv
source .venv/bin/activate        # Mac/Linux
source .venv/Scripts/activate    # Windows (Git Bash)
pip install -r requirements.txt
```

Create a `.env` file in the project root (never committed — see `.gitignore`) with:

```
PGHOST=localhost
PGPORT=5432
PGDATABASE=housing_risk_team
PGUSER=postgres
PGPASSWORD=your_password_here
```

Apply the schema once, before running any notebook:

```
psql -U postgres housing_risk_team -f sql/001_schema.sql
```

Then run the notebooks in order: `01` → `02` → `03` → `04` → `05` → `06`.

For Phase 2, the SQL files must run in this order: `003_phase2_split.sql` → `005_phase4_features.sql` → `003b_cv_fold_membership.sql` (`003b` reads the modeling table `005` builds). `005` drops the `cv_fold_rows` view when it rebuilds the modeling table, so re-run `003b` after every run of `005`. Notebook `02` runs `003` and `003b` and checks their results, but does not run `005`. Notebook `04` runs `005` and then `003b` itself, so the fold view is current after it.

For Phase 3, notebook `03_phase3_eda_merged.ipynb` runs `004_phase3_eda.sql` itself. It needs `train_monthly` (built by `003`) and `mortgage_monthly` to exist.

For Phase 4, notebook `04_phase4_features_merged.ipynb` needs `monthly_split` and `cv_folds` (built by `003`). Its optional last comparisons read the pandas repo's feature matrix from `data/processed/jolenn_train_features.csv` and its summary from `data/processed/jolenn_train_features_meta.json`, and are skipped if the files are missing.

For Phase 5, notebook `05_phase5_modeling_merged.ipynb` needs `quarterly_modeling_table` and the `cv_fold_rows` view (notebook `04` builds both; re-run `003b` after any run of `005`). The baseline lock `docs/phase5_baseline_lock.json` is committed, and a run must reproduce it. If the file is ever deleted, the first run writes it again and stops at the gate cell until it is committed. A full run takes about 3 minutes on an Apple Silicon Mac and about 12 to 35 minutes on a Windows laptop, depending on free memory (the random forest fits use all processor cores, so close memory-heavy programs first). It writes four `phase5_*` tables into the database.

For Phase 6, notebook `06_phase6_evaluation_merged.ipynb` needs `quarterly_modeling_table` and the Phase 5 tables `phase5_validation_predictions` and `phase5_step_summary` (run notebook `05` first). The three lock files in `docs/` (`phase5_baseline_lock.json`, `phase6_thresholds_lock.json` and `phase6_test_lock.json`) must be committed: the notebook reads their git status and stops otherwise, so work in a clone made with git. A run must reproduce the locked cut-offs and the locked Test scores, within the per-family tolerance described in Phase 6. If a lock file is ever deleted, the first run writes it again and stops at its gate cell until it is committed. A full run takes about 15 minutes on a Windows laptop (the random forest refits and the two bootstraps take most of it) and much less on an Apple Silicon Mac. It writes eleven `phase6_*` tables into the database.

### Run everything with make

`make help` lists the steps, and `make all` runs them in order: the schema, notebook `01`, `003`, `005`, then notebooks `02`, `03`, `04`, `05` and `06` (`make phase5` and `make phase6` run those two alone). Executed notebook copies are written to `build/` (ignored by git), so the committed notebooks are never modified. Notebooks `05` and `06` check the git status of the lock files in `docs/`, so run them inside a git clone, and they are slow (about 12 to 35 minutes and about 15 minutes on a Windows laptop). The Makefile works on Mac/Linux and on Windows Git Bash, but GNU make is not installed with Git Bash, so install it first or run the steps by hand.

### What stays on your machine

These are never committed: `.env` (database login), `.venv/`, `data/` (raw downloads and processed files), `build/`, the Postgres database itself, and every file in `outputs/` (the notebooks regenerate them). Everything else can be rebuilt by running the steps above.
